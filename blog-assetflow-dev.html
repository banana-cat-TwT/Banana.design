写在前面

做这个工具的念头其实由来已久。之前项目里那些加载过慢、频繁闪退的问题实在太离谱，严重拖慢所有制作人员的效率，但一直没有人站出来解决，也没人想过要去解决，大家只是抱怨着、忍受着这些痛苦。我当时也有想法，但因为不会实现，就一直只是停留在"想着"。

直到 AI coding 普及，我才真正有能力去动手解决制作过程中的这些痛点，这也是这个工具之所以现在才做的原因。

复盘之后发现，很多问题其实是行业通病。于是决定把当时没来得及做的提效思路，做成一个独立工具AssetFlow。

这篇日志只记录痛点复盘、产品定位、模块规划和当前进度。

痛点复盘）

以下是自研引擎团队普遍会遇到的三类痛点，也是这个工具要解决的核心问题：

1. 引擎启动与加载痛点

· 半自定义引擎依赖命令行 + 文件启动，无可视化封装，操作繁琐；

· 资产全量加载约几十万组，即便硬件配置充足也要耗一整天，开工即晚间；

· 引擎稳定性差，闪退/黑屏/死机频发，单次重启排查耗时约 2 小时起步；

· 无轻量化封装、无分批预加载，只能全量灌入，容错率极低。

2. Git 多仓库多分支协作痛点

· 多独立仓库架构，每轮迭代全量下载，无增量同步，重复无效流量大；

· 切换分支无独立资源缓存隔离，版本错乱、覆盖、缺失频发；

· 大批量资产拉取/推送缓慢，常导致一次开工延后 2～3 天，倘若天天重新加载引擎，后果不堪设想；

· 原生工作流未做分支适配优化，封装软件无法适配多分支资源逻辑。

3. 团队流程弊端

· 岗位分工割裂，无人统筹整条资产管线优化，问题长期搁置；

· 优先级以版本上线、Bug 修复为主，流程提效永久后置；

· 仅有 AI 代码 Bug 预警工具，美术资产管线零自动化。

产品定位

AssetFlow 定位为游戏自研引擎多分支资产一体化轻量化提效工具，完全AI辅助开发，所有问题、需求、优化思路均为研发痛点。

目标：砍掉无效加载、重启、资源同步的全部浪费时间，整体团队生产产能提升 40%。

模块规划

模块一：轻量化可视化引擎封装 开发中

· 桌面可视化一键启动，替代命令行繁琐启动方式；

· 资产分批分时预加载，替代全量灌入，降低负载、减少闪退；

· 崩溃日志自动捕获，缩短排查重启耗时；

· 加载断点续传 / 崩溃自恢复；

· 交互式按需加载（勾选子集先开工，其余后台续载）；

· 离线预热调度（下班后台预热，早上零等待进入）。

模块二：多 Git 仓库多分支增量同步 & 资源隔离 待开发

· 多 Git 仓库批量统一管理，增量同步（仅同步分支变更文件）；

· 每条分支独立本地缓存目录，切换分支自动匹配对应资源；

· 后台预同步调度，规避上班集中加载卡顿。

模块三：轻量化 AI 自动化辅助 待开发

· 本地轻量化资产异常检测（缺失/格式错误/加载异常）；

· 适配美术资产管线的自动侦测、提醒。

当前进度

2026年8月9日，模块一的 A 层（加载断点续传 / 崩溃自恢复）原型已跑通验证。

用纯本地自制测试仓库和合成素材验证了核心链路：把全量加载拆成可记录进度的队列，崩了能从断点续载，把"闪退重来一整天"压缩为"重启续载分钟级"。这一层是整个工具的地基，跑通后后续的按需加载、离线预热都是在它之上叠加增益。

接下来会验证真实引擎侧的"可分批喂入、可中断、可查询状态"加载接口,是下一步的核心工作。

开发模式

延续之前 AI 驱动产品实践的开发模式：需求拆解 → AI 生成实现 → 测试反馈 → 迭代优化。本人负责需求定义、架构设计、测试验证与迭代把控，AI 负责大框架代码生成；针对参数调整、数值配置等小范围修改可独立完成。
